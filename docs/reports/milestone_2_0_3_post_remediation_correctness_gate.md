## 3. In-Depth Audit of Milestone 2.0.1 Remediations

### Audit P1-01 — Multiset Fingerprint Correctness
- **Specification Source:** `SPEC-MOD-02` §2.2, `SPEC-MOD-04` Case 15.
- **Affected Implementation:** `TabularComparator.compare_tables` and `_compute_duckdb_multiset_hash` in `src/data_rewind/comparator/engine.py:679-700`.

#### Technical Evaluation & Proven Properties

1. **Distinction of Concepts:**
   - *Original XOR Defect:* Prior to remediation, `bit_xor(cast(hash(...) as HUGEINT))` was used for $> 5,000$ rows. Because bitwise XOR is self-inverse ($x \oplus x = 0$), duplicate rows occurring an even number of times completely cancelled out to zero, causing tables with duplicate pairs to collide with empty tables.
   - *Ordinary Hash Collisions:* 64-bit integer hashes generated by DuckDB's native `hash()` have collision probability $\approx 2^{-64}$. For a 500,000-row table, the birthday collision bound is $P \approx \frac{(5 \times 10^5)^2}{2 \times 2^{64}} \approx 6.7 \times 10^{-9}$.
   - *Additive Aggregate Collisions:* Summing hashes $\sum h_i$ creates a theoretical subset-sum space. Data Rewind mitigates this by computing **two independent accumulators** with domain salt separation:
     $$\mathcal{H}_1 = \sum_{r \in D} \operatorname{cast}(\operatorname{hash}(\operatorname{json\_object}(r)) \text{ as } \operatorname{HUGEINT})$$
     $$\mathcal{H}_2 = \sum_{r \in D} \operatorname{cast}(\operatorname{hash}(\operatorname{concat}(\text{'__dr_salt__'}, \operatorname{json\_object}(r))) \text{ as } \operatorname{HUGEINT})$$
     $$\text{payload} = \mathcal{H}_1 \mathbin{\Vert} \text{":"} \mathbin{\Vert} \mathcal{H}_2 \mathbin{\Vert} \text{":"} \mathbin{\Vert} |D|$$
     $$\mathcal{H}_{\text{multiset}} = \text{SHA-256}(\text{payload})$$
     An aggregate collision requires simultaneous collision on $\mathcal{H}_1$, $\mathcal{H}_2$, and row count $|D|$.
   - *Exact Equality Verification:* Fingerprint equality is **never** used as the sole proof of dataset equality in Data Rewind. In keyed mode, relational outer joins verify exact equality across all non-key fields (`modified_count == 0`, `added_count == 0`, `removed_count == 0`). In keyless mode, exact multiset frequency joins (`freq_a FULL OUTER JOIN freq_b ON a.h = b.h`) evaluate exact row-level multiplicities. Fingerprint equality functions as an invariant assertion.

2. **Overflow & Cancellation Immunity:**
   - In DuckDB, `HUGEINT` is a 128-bit signed integer with capacity $[-2^{127}, 2^{127}-1] \approx \pm 1.70 \times 10^{38}$.
   - DuckDB's `hash()` returns an unsigned 64-bit integer in $[0, 2^{64}-1] \approx [0, 1.84 \times 10^{19}]$.
   - For the hard limit of 500,000 rows, the maximum possible sum is $500,000 \times (2^{64}-1) \approx 9.22 \times 10^{24}$.
   - The headroom before 128-bit overflow is $\frac{1.70 \times 10^{38}}{9.22 \times 10^{24}} \approx 1.84 \times 10^{13}$ (13 orders of magnitude). **Overflow is mathematically impossible.**
   - Because all summands are non-negative ($h_i \ge 0$), additive cancellation cannot occur ($x + y = 0 \iff x = 0 \land y = 0$).

3. **Determinism & Invariance:**
   - Independent execution verified that DuckDB's `hash(json_object(...))` produces identical 64-bit integer values across separate process executions and memory connections.
   - Row permutations yield identical accumulator sums because integer addition is commutative and associative.
   - Schema differences change `json_object` arguments and `schema_hash`, resulting in different fingerprint digests.

- **Audit Finding Status:** **VERIFIED RESOLVED (PASS)**.

### Audit P2-01 — Collision-Safe SQL Comparison
- **Specification Source:** `SPEC-MOD-04` Case 5, Case 7, Case 13, Case 14.
- **Affected Implementation:** `TabularComparator.compare_tables` in `src/data_rewind/comparator/engine.py:1055-1065`.

#### Technical Evaluation & Adversarial Test Outcomes

1. **NULL vs Literal `'__NULL__'` Sentinel:**
   - Prior implementation: `coalesce(cast(c as varchar), '__NULL__')` mapped both SQL `NULL` and literal string `'__NULL__'` to identical strings, yielding `identical_count = 1`.
   - Remediated implementation: `md5(json_object('col', "col"))`. In DuckDB JSON serialization, SQL `NULL` serializes to token `null` (`'{"s":null}'`), whereas string `'__NULL__'` serializes to quoted string `"__NULL__"` (`'{"s":"__NULL__"}'`).
   - Adversarial verification: `test_audit_p2_01.py` confirmed `identical_count = 0`, `added_count = 1`, `removed_count = 1`.

2. **Delimiter Collision (`'||'` and `','`):**
   - Prior implementation: `concat_ws('||', ...)` allowed cross-column boundary shift (`('x||y', 'z')` vs `('x', 'y||z')`).
   - Remediated implementation: `json_object` encapsulates key-value pairs with JSON object syntax (`'{"a":"x||y","b":"z"}'` vs `'{"a":"x","b":"y||z"}'`).
   - Adversarial verification: `identical_count = 0`, `added_count = 2`, `removed_count = 2`.

3. **Empty String vs NULL:**
   - SQL `""` serializes to `'{"s":""}'`; SQL `NULL` serializes to `'{"s":null}'`.
   - Adversarial verification: `identical_count = 0`, `added_count = 1`, `removed_count = 1`.

4. **Duplicate Multiplicities in Bag Comparison:**
   - Testing 3 copies in table A vs 2 copies in table B:
   - Outer join query on `md5(json_object(...))` correctly computed $\min(3, 2) = 2$ identical, $\max(0, 3 - 2) = 1$ removed, and $\max(0, 2 - 3) = 0$ added. Parity with in-memory `compare` is 100% identical.

5. **Type Preservation in Serialization:**
   - DuckDB `json_object` preserves JSON primitive types:
     - Boolean `true` $\to$ `{"v":true}`
     - Integer `1` $\to$ `{"v":1}`
     - String `"true"` $\to$ `{"v":"true"}`
   - No type coercion or lossy casts occur in row hashing.

- **Audit Finding Status:** **VERIFIED RESOLVED (PASS)**.

### Audit P2-02 — DR-05 Evidence Population
- **Specification Source:** `SPEC-MOD-04` §2.2 (Diagnostic Rule DR-05: Null Sentinel Surge).
- **Affected Implementation:** `src/data_rewind/comparator/engine.py:930-975` and `src/data_rewind/diagnostics/rules.py:250-305`.

#### Technical Evaluation & Rule Contract Analysis

1. **Evidence Population Trace:**
   - In `compare_tables`, when `modified_count > 0`, the engine executes:
     ```sql
     SELECT {cols_select_a}, {cols_select_b}
     FROM (SELECT * FROM "table_a" WHERE {pk_not_null}) a
     JOIN (SELECT * FROM "table_b" WHERE {pk_not_null}) b
     ON {join_sql}
     WHERE NOT coalesce({val_equality_sql}, FALSE)
     LIMIT 100
     ```
   - For each returned row, `TabularComparator.compare_values` evaluates common columns. If a column transitioned from a non-null baseline value to `None`, it generates a `ValueDiff(column=col, baseline_value=..., target_value=None, is_null_transition=True)`.
   - These diffs populate `RowDiff.field_diffs` in `sample_row_diffs`.

2. **SQL 3-Valued Logic Correction:**
   - During the audit, an edge case in SQL 3-valued logic was verified: if a column is `FLOAT`/`DOUBLE`, `abs(val - NULL) <= tol` evaluates to `NULL`.
   - Remediated implementation explicitly guards float clauses:
     `((a.c IS NOT DISTINCT FROM b.c) OR (a.c IS NOT NULL AND b.c IS NOT NULL AND abs(a.c - b.c) <= ...))`
     and wraps `val_equality_sql` in `coalesce(..., FALSE)`.
   - Rows transitioning to `NULL` evaluate strictly to `FALSE`, ensuring `NOT coalesce(..., FALSE)` evaluates to `TRUE`. The row is correctly classified as `MODIFIED`, and the mathematical partition invariant holds.

3. **Sampling Boundary:**
   - `sample_row_diffs` is bounded to `MAX_SAMPLE_DIFFS = 100` modified rows, 25 removed rows, and 25 added rows to guarantee memory safety (< 512 MiB RSS).
   - DR-05 inspects `sample_row_diffs` and reports:
     `"Column 'col' experienced a null surge ({count} sample rows transitioned from non-null values to NULL)"`.
   - The finding explicitly characterizes the observation as sample-backed, adhering to the `PROVEN_OBSERVATION` tier contract.

- **Audit Finding Status:** **VERIFIED RESOLVED (PASS)**.

## 5. Residual Findings Register

No P1 or P2 correctness defects remain. The following P3 items represent documented architectural boundaries:

### Residual Finding R-01: Dual Multiset Hash Algorithms Across Table Sizes (P3 - Bounded Architecture)
- **Description:** Tables $\le 5,000$ rows compute multiset hashes via in-memory 256-bit integer sums of SHA-256 canonical rows (`compute_multiset_hash`). Tables $> 5,000$ rows compute multiset hashes via DuckDB's in-engine dual 128-bit additive accumulator (`_compute_duckdb_multiset_hash`).
- **Impact:** Both algorithms strictly preserve row multiplicity, order invariance, and distinguish NULL from sentinels. However, the resulting 64-character hex strings are computed from different hash primitives and cannot be directly compared between an in-memory run and a large DuckDB table.
- **Classification:** Documented architectural boundary. Essential to satisfy the $< 1.5$s execution target on 500k rows.

### Residual Finding R-02: Bounded Sample Size for Diagnostic Rule DR-05 (P3 - Sampling Boundary)
- **Description:** `sample_row_diffs` is capped at `MAX_SAMPLE_DIFFS = 100` modified rows to maintain process memory limits (< 512 MiB RSS). In massive tables with sparse null transitions appearing strictly after row 100 in physical scan order, DR-05 will not encounter sample evidence.
- **Classification:** Documented sampling boundary. DR-05 finding messages explicitly qualify findings as sample-backed observations.

### Residual Finding R-03: Heuristic Sequential DAG Inference on Omitted Dependencies (P3 - API Fallback)
- **Description:** When `step_dependencies is None`, `detect_eod` infers a linear pipeline from `topological_order`. If a non-linear DAG with parallel branches omits dependency metadata, concurrent divergence points will be serialized as a linear chain.
- **Classification:** Documented API contract. Callers requiring multi-branch concurrent divergence isolation must pass the explicit adjacency dictionary.
